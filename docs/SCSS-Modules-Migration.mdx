# SCSS Modules migration

Simorgh is migrating component styling from Emotion CSS-in-JS (`ThemeProvider`) to SCSS Modules + CSS custom properties (`ThemeProviderSCSSModules`).

This page covers **how the migration is being sequenced**. For the styling rules themselves, see [Coding standards: Styles](https://github.com/bbc/simorgh/blob/latest/docs/Coding-Standards/Styles.mdx).

## Scope

This programme covers `src/app/components/**` only. Components under `src/app/legacy/**` — including `containers/` and `psammead/` — are explicitly out of scope for now, as is page-level styling in `ws-nextjs-app/pages` (for example `live/[id]`, `av-embeds`, `my-news`).

Legacy components need modernisation *and* a styling change. Converting them to SCSS Modules now would invest effort in code that may later be removed or rewritten. They are handled after the modern set, and each one gets one of three decisions:

- **Delete** — nothing uses it any more.
- **Fold in** — still used, but doesn't warrant being its own component. Inline it into its consumer, or merge it into an existing modern component that already does the same job.
- **Modernise and convert** — it earns its place, so bring it up to current standards and move it to SCSS Modules.

## Definition of done

This programme is complete when `src/app/components` contains no imports from `@emotion/*`, no `index.styles.*` files, and no `css` props. The last check matters because `tsconfig.json` sets `jsxImportSource` to `@emotion/react` globally, so a component can use Emotion's `css` prop — as `Heading` and `Paragraph` currently do — without importing `@emotion` or having its own `index.styles.*` file.

## Current status

The initial Batch 1 migration is complete. As of October 2026, the latest branch contains:

- 15 `index.module.scss` files under `src/app/components`.
- 82 remaining `index.styles.*` files under `src/app/components`.
- Production components currently using SCSS Modules include `Copyright`, `ReadTime`, `InlineLink`, `ArticleLinksBlock` and its `Promo`/`PromoList` children, `Curation/Subhead`, `EmbedError`, `SaveButton`, `FollowTopicButton`, `ActionTooltip`, `EpisodeDescriptionFormatter`, and both `GooglePreferredSource` link components.
- `Example/index.module.scss` is a reference implementation rather than a production migration.

The SCSS Modules foundation and service themes are now established. The remaining work is the incremental removal of the 82 Emotion style files, with legacy-coupled and AMP/Lite components still requiring the dedicated decisions described below.

## Lessons from the first migration batch

The component migrations happened in [PR #14371](https://github.com/bbc/simorgh/pull/14371), which was merged into [PR #14332](https://github.com/bbc/simorgh/pull/14332) before that work reached `latest`. [PR #14410](https://github.com/bbc/simorgh/pull/14410) then followed up on the typography API and documentation. The review process exposed several changes to the migration plan.

### Audit consumers before deleting Emotion styles

The owning component is not the whole styling contract. Before removing an `index.styles.*` file, search every consumer for:

- **Consumer `css` overrides:** Find overrides such as `Disclaimer`'s `css={styles.inlineLink}` before deleting the shared style file. Either migrate the consumer's override, keep a compatibility path, or stop and report the consumer as blocked; otherwise the prop may reach the DOM unused and silently lose its styling.
- **Replacing rather than composing classes:** Check every consumer that supplies `className`. `EmbedError` originally passed a module class to `InlineLink`, which replaced `InlineLink`'s default `focusIndicatorReducedWidth` class. Preserve shared defaults by composing classes or making the shared component merge its own class with consumer classes.
- **Direct helper imports:** Search for consumers importing helpers from `index.styles.*`. The legacy send-form pages imported `InlineLink` style helpers, so those styles had to be localised in the page tree before the component's Emotion style file could be removed.
- **Contextual cascade overrides:** Identify which component owns each default, visited, hover, focus, and focus-visible state. For example, move an `EmbedError` default-state override into a meaningful ancestor selector such as `.errorLinkWrapper .inlineLink`, leave `:visited`, `:hover`, and `:focus` to `InlineLink` when it owns those states, and do not rely on Emotion's stylesheet injection order. Verify the result in AMP/Lite as well as canonical output because stylesheet order and inlining differ by edition.

### Treat typography as two APIs

Typography has a compile-known path and a runtime path. When scale and variant are SCSS literals, use `typography-from-scale-and-variant`. When values arrive as React props, use the typed `getTypographyCustomProperties` helper with `typography-from-custom-properties`. Sass variables and mixin arguments cannot consume React runtime values.

Use GEL typography breakpoints for typography, not layout breakpoints: Group B begins at 320px and Group D at 600px. Test the compiled Sass output for all responsive groups and test the runtime helper's custom-property mappings independently.

Font fallback aliases are part of the public typography contract. Compare a new alias chain with the legacy resolver before changing it, especially for variants such as `serifRegular`, where fallback order affects font weight.

### Expand verification beyond Jest

Jest mocks `.module.scss`, so component tests cannot validate compiled selectors, Sass mixins, cascade order, or service theme output. Every migration batch should include:

1. Focused component tests for DOM/class/attribute contracts and consumer overrides.
2. A production build to catch SCSS, TypeScript, and deleted-style-file consumers.
3. Sass contract tests when shared typography or theme mixins change.
4. Browser or Storybook/Chromatic checks for RTL, dark UI, responsive typography, and AMP/Lite-rendered components.

Snapshots are useful for structural changes, but they are not a substitute for compiled-CSS or visual verification.

### Order by contract risk, not only style size

The first batch was small by style-line count, but `InlineLink` was a shared primitive with many consumers and therefore had a larger contract surface than its size suggested. Future batches should score shared components by consumer count, runtime props, legacy consumers, service/theme sensitivity, and AMP/Lite exposure before assigning them to an early batch.

### Measure AMP/Lite during the migration

The CSS payload investigation found that the SCSS theme adds a fixed cost to AMP/Lite, where CSS is inlined and subject to AMP's 75 KB limit. Measure representative production pages after each meaningful batch and do not introduce CSS reordering optimisations without browser-level computed-style comparisons. A media-query compaction experiment saved bytes but produced real cascade regressions when elements carried multiple generated classes.

The existing `amp:validate` check now includes the large Russian article fixture (`c6wyzl2xdyz2o`). The production local fixture measures 68,169 bytes against 69,116 bytes on the live page, and `amphtml-validator` fails with `STYLESHEET_TOO_LONG` above the 75,000-byte limit. This is a hard-limit guard, not an early-warning budget report; add further representative fixtures or explicit byte reporting if migration headroom becomes difficult to track.

## Batching principles

Work is submitted in small PRs so review stays tractable.

- **Size by style-line count, not component count.** Three 20-line components is a very different review from three 250-line ones. Roughly 150 lines of style per PR keeps review effort consistent.
- **Delete the `index.styles.*` file in the same PR.** Never leave two sources of truth for one component.
- **Order by risk**, using the four axes below.

### Risk axes

| Axis | Lower risk | Higher risk |
|---|---|---|
| Blast radius | Used in one or two places | Shared primitive used across many pages |
| Test churn | No `__snapshots__` folder | Has snapshots |
| Verification effort | Canonical only | Also renders on AMP or Lite |
| Coupling | Self-contained | Renders, or passes styles into, an Emotion-styled legacy component |

Most components have no snapshots, so snapshot churn is limited and predictable.

## Blocked components

These cannot be fully migrated without a decision that goes beyond styling. Keep them out of the styling-only batches described above — each needs its own piece of work.

| Component | Blocker |
|---|---|
| `Disclaimer` | Renders `GridItemLarge` from `legacy/components/Grid` |
| `MostRead/Canonical/Item` | Renders `Grid` from `legacy/components/Grid` |
| `MostRead/Canonical/List` | Renders `psammead-grid` |
| `MostRead/Label` | Passes a `css` prop into `psammead-section-label`, and uses a palette value as a runtime prop |
| `RelatedTopics` | Passes a `css` prop into `psammead-section-label`, and uses a palette value as a runtime prop |
| `Recommendations` | Passes a `css` prop into `psammead-section-label`, and uses a palette value as a runtime prop |
| `RelatedContentSection` | Imports a legacy Emotion styles file directly (`OptimoPromos/PromoItem/index.styles`) |

For the grid cases, our styling standards direct us away from `psammead-grid`, so these need a native layout replacement rather than a like-for-like port.

Rendering a legacy component is not itself a blocker. `ArticleLinksBlock` renders `SkipLinkWrapper` and migrated fine, because the legacy child is self-contained and keeps its own styles. The problem arises when the legacy child **controls the layout of your content**, or when styles are **passed into** it.

Legacy imports that are **pure utilities** never block migration. For example `ReadTime` imports `formatDuration` from `psammead-timestamp-container`, which has no styling implications.

## Deferred to the end

- **AMP and Lite components** — `Ad/*`, `MostRead/Amp`, `AmpIframe`, `Embeds/AmpIframeEmbed`, `MediaLoader/Amp`. Grouping these lets them share a single round of manual testing on the AMP platform rather than requiring one per batch.
- **The largest components** — `Curation/HierarchicalGrid`, `MostRead/Canonical/Rank`, `Navigation`, `CollapsibleNavigation`. Each warrants a dedicated PR rather than sharing one.
- **Components with heavy legacy coupling** — `MostRead`, `Navigation` and `Curation` hold most of the remaining legacy imports.

## Revised sequence

The original batches grouped components by approximate size and cohesion. The first migration showed that the more important measure is the contract surface: consumer count, runtime props, accessibility behaviour, theme/service inputs, pseudo-states, and dependencies on other Emotion components.

| Order | Scope | Reason for the revised order |
|---|---|---|
| 1 | `Spinner` | Small visual contract with a focused class-composition check on the underlying icon. |
| 2 | `VisuallyHiddenText` | Simple styles but roughly 200 consumers; give the high fan-out primitive its own PR and accessibility verification. |
| 3 | `LiveText` | Follow `VisuallyHiddenText`; it combines service translations, direction, screen-reader behaviour, and live-label typography. |
| 4 | `Footer/Link` | Handle separately because it combines runtime visibility, dynamic display, focus inversion, hover/focus states, and a consumer in `ActionTooltip`. |
| 5 | `Curation/CurationMessageBanner` | Defer until its `Heading`, `Text`, and `MessageBanner` styling contracts are understood or migrated; it currently passes Emotion styles into shared children. |
| 6 | `CallToActionLink` and its sub-components | Keep the family together, but treat it as a dedicated higher-risk PR because it has several consumers, inherited text styles, nested pseudo-state selectors, and consumer `css` overrides. |

## Next steps

1. **Start with `Spinner`**, then give `VisuallyHiddenText` its own high-fan-out migration PR.
2. **Migrate `LiveText` after `VisuallyHiddenText`** and verify that the styling change preserves its functional output: translated live-label text, the `dir` value, `aria-hidden` states, visually hidden screen-reader text, typography, and AMP/Lite rendering.
3. **Audit `Footer/Link` consumers before migrating it**, especially `ActionTooltip` and the `focusIndicatorInvert` contract.
4. **Do not migrate `CurationMessageBanner` in isolation** until its shared `Heading`/`Text`/`MessageBanner` styling boundaries are resolved.
5. **Plan `CallToActionLink` as a dedicated PR** with a complete consumer audit rather than treating its sub-components as a low-risk batch.

## Ongoing guardrails

1. **Measure representative AMP/Lite pages after each meaningful batch.** The migration has a fixed theme cost, and Arabic AMP is the closest measured page to the 75 KB limit; use production builds and real rendered pages rather than Jest's mocked SCSS output.
2. **Maintain representative AMP fixture coverage.** The existing validator now guards the large Russian article against AMP's 75 KB hard limit; add another local fixture when a different service or page shape becomes the new high-water mark.
3. **Do not use CSS reordering as a migration shortcut.** The abandoned media-query compaction experiment produced real computed-style regressions when elements carried multiple generated classes. Any future CSS transformation must be verified with browser-level computed styles across representative viewports.

## Tooling

Migrations are largely done by AI. Two files tell it how:

- `.github/instructions/styling-standards.instructions.md` — the styling rules, applied automatically whenever a file in `src/app/components` is edited.
- `.github/skills/migrate-component-to-scss-modules/SKILL.md` — the step-by-step conversion process, including the Emotion-to-SCSS value lookup and the checks listed above.

This page isn't read by the AI. It's here for engineers planning the work.

## Verifying a batch

1. Run the component's tests. Regenerate snapshots only where the component has a `__snapshots__` folder, and review the diff — class-name churn is expected, structural DOM changes are not.
2. Confirm no `@emotion` imports remain in the migrated component.
3. Check an RTL service (for example `arabic`) and a dark UI context. Those two behaviours move out of JavaScript branching and into SCSS selectors, so they are the most likely regressions.
